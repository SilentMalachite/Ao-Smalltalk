# P12 — Browser の削除（設計）

## 結論

System Browser から、間違えて定義したメソッドとクラスを消せるようにする。C ABI に `ao_remove_method` と `ao_remove_class` を足し、Browser の右クリックメニューと Smalltalk メニューから、確認のシートを経て呼ぶ。正本は SPEC §3.9「削除」、§3.10、§6「Browser の削除」である。本書は設計判断の理由を残す。

## 前提

- P11 は受け入れ済み（`97bb489`）。P12 は v1 のあとのフェーズとして SPEC §2.3 に足した。
- メソッド辞書（`MethodDictionary`）は、キーと値を交互に並べた配列を線形に引く。削除の関数は無い。
- グローバル辞書（`Smalltalk`）も同じ形で、キーが nil の対を空きとし、登録は最初の空きを使う。SPEC は「v1 ではグローバルを消さない」としていたので、これを改めた。
- キャッシュの無効化は `invalidateMethodCache(cache, selector)` の 1 か所を通る（selector が空ならキャッシュ全体）。
- 生きているサブクラスの判定は `hasSubclass`（Compile.cpp。§3.9「クラス定義の再 Accept」の定義）がある。
- ソース表はイメージに書かない。イメージを読み直すと、Browser で定義したものと vendor のものを区別できない。

## 利用者との合意（2026-09-26）

| 論点 | 決定 |
|---|---|
| 消せる対象 | Kernel 以外すべて。メソッドは CompiledMethod ならクラスによらず消せる（`Object>>foo` も）。NativeMethod は拒む。クラスは Kernel クラスと固定のグローバルを拒む |
| クラスの削除とサブクラス | サブクラスがあれば拒む。名前を参照するメソッドは許す（実行時に nil を読む）。既存インスタンスは旧クラスのまま動く |
| UI | 右クリックメニューと Smalltalk メニュー、実行前に確認のシート |
| ワークスペース変数（2026-09-26 追記） | 消した名前は未定義の識別子に戻る。グローバル名の版を進めて `knownGlobals` を作り直すだけで、同名のワークスペース変数には触れない（クラス定義より古い束縛が再び見える） |
| 右クリックの順序（同） | メニューは右クリックした行を対象にし、項目を選んだ時点で「破棄の確認 → 行を選ぶ → 削除の確認」を順に出す。コンテキストメニューは同期して開くので、非同期のシートを先に出せない |
| メッセージの名前（同） | `<name>`/`<Class>` は渡した `class_name` そのまま、クラス側は ` class` を付ける。`carriedMethodName` と確認のシートと同じ書き方 |

## 方式

**採用: C ABI に削除関数を 2 つ足す。** Accept（`ao_accept_method` / `ao_accept_class`）と同じ経路、同じ busy 判定、同じ `AoSpan.message` で理由を返す。

**不採用: Smalltalk 側に `removeSelector:` / `removeFromSystem` を足し、`ao_eval` で呼ぶ。** Kernel のネイティブを増やすうえ、ホストが評価文字列を組み立てることになり、拒否の理由も評価エラーの文字列に混ざる。v1 の方針（ネイティブ Kernel を薄く保ち、ツールはホストに置く）にも合わない。

## 設計判断

### メソッドの削除

- 対象はその側のメソッド辞書にあるセレクタだけ。継承したものは消さない。Browser のセレクタ一覧も継承したものを出さないので、見えているものだけが消える。
- NativeMethod を拒むのは、Kernel 走査（全 Kernel メソッドが NativeMethod）とネイティブ必須セレクタの契約を守るためである。CompiledMethod は Kernel クラスの上にあっても消してよい。走査は NativeMethod だけを確かめるので、結果は変わらない。
- 手順は「辞書から除く → そのセレクタのキャッシュを無効化 → ソース表の項目をブロックごと外す」。辞書は線形なので、対を nil にして `tally` を 1 減らせば、残りはどれも引けるままである。割り当ては無い。
- 実行中のフレームは消す前のメソッドを持ったまま走る。再 Accept と同じ扱いで、新しい規則は要らない。

### クラスの削除

- 外すのは、指定した名前の `Smalltalk` の束縛だけである。クラスオブジェクトには触れない。インスタンスが残っていても安全で、別名も残る。これは Smalltalk-80 の `removeFromSystem` に近い、最も小さい操作である。
- 固定のグローバル（vendor のスタブを含む 56 のクラス名、`Processor`、`Smalltalk`）を拒むのは、well-known 表がそれらを名前と別に保持しており、束縛だけを外すと表と辞書が食い違うからである。Kernel クラスの別名は同一性で拒む（`ao_accept_method` の規則と同じ）。
- サブクラスの判定は `hasSubclass` をそのまま使う。名前の無いサブクラスや、形の変更で残った旧クラスも数える。ここで拒否しておけば、「スーパークラスの名前が消えたクラス」が Browser の定義テキストに現れることはない。
- キャッシュは全体を捨てる（クラスの差し替えと同じ）。ソース表からは、そのクラスの両側のメソッドの項目を外す。
- その名前を読むメソッドはコンパイルし直さない。`PushGlobal` は無い名前を nil として読む（既存の規則）。
- ワークスペースの `knownGlobals` は `WellKnown::globalsVersion()` が動いたときだけ作り直される。削除でも版を進めないと、消した名前は次にクラスを定義するまで `PushGlobal` のまま残り、その後に突然ワークスペース変数へ変わる。版を進めれば、消した名前は既存の規則（未定義 → ワークスペース変数、クラスは束縛より勝つ）の逆をたどるだけで、新しい状態は要らない。同名の古い束縛を消してまで nil を保証する案は、削除がワークスペースの状態に手を伸ばすので採らない。

### 共通

- 成功は `AO_OK`、拒否は `AO_ERR` とメッセージ（`ao_image_load` と同じ形）。`AO_ERR_COMPILE` は使わない。コンパイルとは関係が無いからである。
- busy の間は拒む。busy の入口の一覧に 2 つを足す（ヘッダの説明の数も直す）。
- 拒否したときは、何も変えない。検査をすべて済ませてから書き換える。

### Browser

- 既存の `confirmDiscard`（差し替え可能な確認）と同じ形で、削除の確認も差し替え可能にし、XCTest からシートを出さずに答えを与える。
- 右クリックのメニューは AppKit が同期して開くので、破棄の確認（非同期のシート）を先に出せない。メニューは `clickedRow` を対象にし、項目を選んだ時点で「破棄の確認 → 行を選ぶ → 削除の確認 → ABI」を順に進める。削除の確認で Cancel すると選択の変更だけが残る。
- メニュー項目の有効・無効は `NSMenuItemValidation` で決める。キーウィンドウを引数で受ける純粋な判定にして、XCTest がキーウィンドウに頼らずに確かめられるようにする。
- 一覧は導出値なので、削除のあとは `model.refresh()` と `publish()` で読み直す。空になったプロトコルとカテゴリは自然に消える。
- 拒否されたときはエラー欄（既存の `makeErrorField`）に理由を出す。

## 範囲

**やる:** `ao_remove_method`、`ao_remove_class`、`MethodDictionary` と `Globals` の削除、ソース表の項目の除去、Browser のメニューと確認、テスト、SPEC と CHANGELOG。

**やらない:** Undo、削除したソースの保存、サブクラスごとの削除、プロトコルやカテゴリの名前変更、Smalltalk 側の削除セレクタ、クラスの名前変更、Workspace やファイルからの削除コマンド。

## テスト

- runtime（GoogleTest）: `remove_abi_test`。SPEC §4.1 に挙げた各テスト。キャッシュ済みの送信、NativeMethod と固定のグローバルと別名とサブクラスの拒否、ソース表、busy、拒否で何も変わらないこと、保存とロード、Kernel 走査。
- app（XCTest）: SPEC §4.3 に挙げた各テスト。メニューの有効・無効、右クリック、確認と Cancel、一覧の更新、拒否の表示、破棄の確認が先であること。
- 既存: `ao --test image/tests`、`gcstress`、`gcstress_vendor`、Kernel 走査を緑のまま保つ。

## リスク

- メソッド辞書やグローバル辞書を `instVarAt:put:` で壊した場合の削除は、既存の「壊れた表」の規則に従い、メモリの安全だけを保つ。
- `hasSubclass` はヒープ全体をたどるので、クラスの削除は O(ヒープ) である。操作は Browser からの手動の 1 回なので許容する。

## 追補: クラス ID（2026-09-27）

### 問題

Browser の行はクラスの名前スロットで名付けられ、ABI はどの呼び出しもクラスを名前で引いていた（読み出しは一覧の中で同じ名前の最初の行、Accept と削除は `Smalltalk` の束縛）。`Foo`（カテゴリ Old）を定義して `Smalltalk at: #Alias put: Foo` とし、`Foo` を消してから新しい `Foo`（カテゴリ New）を定義すると、Old の `Foo` の行は旧クラスなのに、その行の Remove Class… は新しい `Foo` の束縛を外し、読み出しは新しいクラスのメソッドを見せることがあった。一覧のソートは安定でないので、どちらの行が先かも決まらなかった。あわせて、`MethodDictionary::at` が壊れたメソッド辞書（`instVarAt:put:`）の範囲の外を読み、送信で落ちることがわかった。

### 利用者との合意（2026-09-27）

| 論点 | 決定 |
|---|---|
| 範囲 | Browser 全体をクラスの同一性で指す。クラスを指す Browser の ABI はどれも名前でなく ID を取る（プロトコルとセレクタの一覧、ソース、定義、スーパークラス、サブクラス、Browser からの Accept、`ao_remove_method`、`ao_remove_class`）。行は ID を持ち、Swift は選択を ID で持ち、名前を見せる |
| クラスの削除 | 外すのはクラス自身の名前の束縛だけで、それがこのクラスを指しているときに限る。別名は残す（今までの規則）。自分の名前に束縛されていないクラスの行（別名だけが持つ旧クラスなど）は理由を付けて拒み、何も変えない |

### 方式

- ID はセッションの表（ID → クラス）の正の整数で、OS のプロセスの中で使い回さない（Scheduler の pid と同じ単調な数）。表の枠はルートで GC が更新する。ソース表と同じく、イメージの保存と生存の判定（`liveClasses`）はそこからたどらない。表だけが持つ削除済みのクラスがイメージに入ったり、スーパークラスの削除や形の変更を妨げたりしないためである。
- ID は一覧に出るクラスにだけ付け、一覧を作るたびに一覧から消えたクラスの項目を外す。ID を取る呼び出しはどれも一覧を作るので、消えたクラスの ID はすぐ未知になり、`unknown class id` で拒まれる。
- 一覧は 1 クラス 1 行にした。別名で 2 回束縛されたクラスが同じ ID の 2 行になると、選択を ID で保てないからである。同じ名前の行は ID の小さい順（古いクラスが先）に並べ、順序を決める。
- 新しいセッション（boot、ロード）は空の表で始まる。ロードのあとで ID を続けられる手掛かりは名前しか無いので、Browser は選んでいた行の名前に今束縛されているクラスを選び直す。
- Accept は、名前で引く `ao_accept_method` を残し（135 の呼び出し元の多くはテストと名前から始める用途）、Browser 用に `ao_accept_method_id` を足した。規則は同じである。
- 壊れたメソッド辞書は、`removeKey` と同じ形の検査（配列の枠を持つポインタのオブジェクトで、配列もポインタのオブジェクト）を `MethodDictionary` の 1 か所（`pairArray`）にまとめ、`at`、`atPut`、`removeKey`、`Behavior>>selectors` がそれを通る。形が合わなければメソッドが無いものとして扱い、送信は上位クラスか `doesNotUnderstand:` に進む。

### 採らなかった案

- **`identityHash` を ID にする:** ヘッダの hash は 16 ビットで、クラスが増えれば重なり、使い回しも起きる。行の同一性を保証できない。
- **クラスの枠に ID を持たせる:** クラスの形（`kClassSlotCount`）とイメージ形式を変えることになり、Kernel クラスとブートストラップと `.aoimage` の検査にまで手が入る。セッションの表なら、Smalltalk のオブジェクトにもイメージにも触れない。
- **名前のまま、確認だけを足す（削除の前に行の名前が今そのクラスを指すか確かめる）:** 削除の誤りは防げても、同じ名前の 2 行の読み出しと Accept は区別できない。行の同一性はどの呼び出しにも要る。
